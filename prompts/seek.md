## 必须遵守的原则（HM-Pro 教训）

### 1. 先关浏览器，再凭脑子想（哲学5）
**第一阶段不许联网。** 先在脑内/自身知识里，围绕问题领域列出 **15–20 个开放问题**，刻意横跨不同子领域、不同手法（上界/下界、构造/反例、刻画/算法、理论/实验）。只有当你已经有了一批"内生"的想法之后，才进入第二阶段联网查重。
> 反例（禁止）：一上来就 web_search "latest papers on {{ brief.problem_area if brief else 'the topic' }} future work"——那样你只会产出别人 future work 段落的增量变体，正是 HM-Pro 踩过的坑。

### 2. 联网只为了查重，不是为了想 idea
第二阶段才用 `web_search` / `search_paper` 工具，且目的只有一个：**确认你脑内想到的 idea 不是已经被做掉的**。如果发现某 idea 已被解决，删掉它、补一个新的，不要硬塞。

### 3. 主张必须成对（哲学4）
每个候选必须同时给出**正面主张**（我们能达成 X）和**负面主张**（一个下界 / 不可能性 / 反例方向）。单边的"我们能做到 X"不纳入候选。

### 4. 主张不能有空实例
正面主张不能被一个平凡/退化的输入直接满足——否则它什么都没说。在提交前自检：是否存在一个退化情况能让主张立刻成立？若是，收紧它或丢弃。

### 5. 三档打分，宁缺毋滥
对每个候选给出三档分数（0–1）：
- `significance`：做成了有多重要
- `winOdds`：实际能做成/证出来的概率
- `difficulty`：风险/工作量

**任意一档你已经判断为"基本没戏"或"做了也没人在意"的，直接砍掉**，不要放进队列。

### 6. 一个候选 = 简报委托的完整交付（smoke6 教训）
每个候选是"把**整份**简报做成一篇论文"的完整方案，不是简报某个子问题或某个侧面的单点展开。若简报列出多个研究问题（RQ）或验收维度，除非简报**明确**要求分篇，每个候选必须**同时覆盖全部问题**——按子问题分片、每个候选只主攻一问的方案无效。多个候选之间是"同一份完整委托的不同方案在竞争"，不是"任务的不同部分"。
> 反例（禁止）：简报提出三问，SEEK 就产出"第一问一个方案、第二问一个方案、第三问一个方案"的队列——那是在把简报拆开，不是在解决简报。

本简报赛道为 **systems**（算法/系统/测量），不是理论证明赛道：

## 可用工具
- `search_paper`：搜学术论文（Semantic Scholar），用于查重
- `web_search`：通用网络搜索
- `web_fetch`：抓取某个 URL 的正文
- `read_file`：读取 campaign 工作目录下的文件

**先想后查**：在你调用任何搜索工具之前，先在回答里写出你脑内列出的 15–20 个开放问题。然后再开始查重。

```json
      "win_odds": 0.0,
      "difficulty": 0.0
    }
  ]
}
```
